## 2026-09-28 T3

- 提醒触发点默认值（计划 4.3 允许默认）：date 型 = 截止日当天 09:00（任务 due 时区）；instant 型 = 截止时刻前 24 小时。任务 schema 暂无用户自选提前量字段，V1 不提供选择；加字段时属后续任务。
- reminderRevision 递增的字段映射（计划 8.2 只列"截止、提醒规则、终态、归档、重开"）：due 三列任意变化、状态变为 done/cancelled、从 done/cancelled 重开、归档。scheduled_start/end 与 plannedWeek 变化不递增——V1 提醒只基于 due。标题/备注变化不递增，正文在准入时用最新标题生成（符合 8.2"未准入邮件使用发送时最新标题"）。
- "提醒未过期"的实现解释：越过 due 边界（date 型当地次日 00:00；instant 型 at 本身）即视为过期，job 以 skipped/overdue 结束不发送，任务自然出现在逾期与待处理列表，不补发无意义提醒。
- 过去触发点不建 job（8.2"过去触发点进入今日待处理"）：`GET /notifications` 的 pendingReminders 按此口径查询呈现；notifications 是最小实现（pending/upcoming/在途旧投递/近期投递四段），不是完整通知中心。
- jobs.type 不用 CHECK 封死枚举，T4+ 新类型免迁移；`POST /jobs/:id/cancel` 只放行 reminder 类型（计划：取消接口只允许可见可取消的作业类型）。
- worker 单实例前提：recoverOnStartup 越过 token fencing 直接恢复孤儿 job/在途 delivery，理由是"一个实例一个 worker、启动时不存在其他执行者"（计划 8.1 允许一个 worker 遵守这些规则处理异常重启重叠）；恢复把 submitting→unknown 且对应 job 落 done，不自动重发。
- Mailer 注入：`setMailerForTests` 覆盖 `resolveMailer()`；SMTP 未配置返回 null，调用方报 503 INTEGRATION_UNAVAILABLE。测试邮件（mail/test）的 delivery 没有父 job，用独立随机 lease_token 满足 markOutcome 的条件更新。
- `POST /mail/preview` 与 `/mail/test` 不要求 Idempotency-Key：preview 不创建任何资源；test 是主人显式点击的一次性动作（产生 delivery 记录但无幂等创建语义），重复点击即重复发送，与"unknown 重发提示可能重复"的处理一致。
- settings 行不存在时 version=0 表示首次创建（PATCH expectedVersion=0 为 INSERT，主键冲突返回 409）；模板配置存 settings 表 `mailTemplate` 键，读取时与 Zod 默认值合并。

  - 排除：owner、sessions、idempotency_keys、jobs、deliveries、ai_usage、exports、instance_state、planning_state、schema_version。
  - inbox_sources 去掉 token_digest；settings 去掉调度内部键；各类 job_id 列去掉。

  - 成果：所选成果。
  - 困难：所选记录的卡点 + 结束判断理由。

## 2026-09-30 待修清单 4、6、7、8 与 F19

- 登录限速放内存：web 单进程，重启清零可以接受，不为此加表。按来源地址每 15 分钟 10 次失败，另设全局 100 次防换地址穷举；达到上限时连正确密码也先返回 429（否则限速对猜中的那次无效）。成功登录清掉该地址计数。来源取 `X-Forwarded-For` 最后一跳：web 只监听环回，前面的 Caddy 不信任客户端传来的 XFF（未配 trusted_proxies），会用真实地址覆写。
- 外键失败统一映射为 422 `INVALID_REFERENCE`：`runIdempotent` 兜住所有创建，任务/项目 PATCH 和记录 POST 用 `withReferenceCheck`。不在每个路由里逐个预查 ID——数据库外键已经是唯一可信判据。
- 首页近期行动按 v1.2 第 4 节重排：今天 = 今天计划（时段开始在今天）或今天截止；临近 = 未来 7 天内的时段或截止；本周未定时 = 归属本周。三者都不满足的任务不上首页（此前被归到"临近截止"）。组内先有具体时间的，再高优先级，再创建顺序。分类挪到 `src/domain/today.ts` 以便单测。
- 显式重发（unknown/failed）：由 web 进程直接发送（与测试邮件同一路径），不经 worker、不自动重试。沿用原投递的收件人与正文快照，只换新 requestId、attempt+1；新列 `deliveries.resent_from` + 部分唯一索引保证同一条原投递只能重发一次，重复点击 409。提醒类要求任务未结束且 reminderRevision 未变，改期后的旧提醒不重发（新提醒由 job 负责）。请求必须带 `confirmDuplicateRisk: true`，界面两步确认并说明可能收到两封。
- web 进程发送（测试邮件、重发）若在 submitting 时崩溃会停在 submitting：worker 启动恢复只处理 job 发起的投递，这一点与测试邮件既有行为一致，未改。
- DST（F19）：`resolveWallTime` 以当天前后 24 小时的两个偏移为候选，逐个验证；两个都成立 = 重复时刻取较早 instant（overlap_earlier）；都不成立 = 落在跳过区间，二分到转换点（gap_shifted）。`wallTimeToUtc` 保持签名不变。周期 occurrence 的唯一键尚未包含"选择的偏移"，调整标记也还没持久化到 occurrence（当前实例时区 Asia/Shanghai 无 DST，不影响）。

## 2026-10-04 Agent 自由度与统一交互

### 决策依据

主人要求统一 Agent 输入栏，保留自然语言；卡片动作携带 `/指令` 与对象上下文。后续实际使用发现“查看安排”误建任务，“根据每天的课程重新安排时间”因缺具体日期/钟点被拒绝。主人明确要求这类模糊指令给予 Agent 更大自由度。

### 已采用的决策

1. **输入统一，语法不是决策能力。** 页面共用输入栏；`/指令` 帮助限定意图，不能变成强制用户填参数的表单。明确句式仍可快速解析；模糊时间调整进入读取实际状态的模型决策。
2. **查询保持只读。** 查看、查询、解释当前数据返回事实和导航，不创建“查看……”任务、不改安排、不提供虚假的撤销。`/查看` 的正文不能触发修改。
3. **主人给目标，Agent 补执行方案。** 调整读取实际课表、固定活动、共享预算、未完成任务、目标与现有安排；能合理选择时给出依据并执行有边界的重排/临时每日上限。缺少具体钟点本身不是追问理由；缺失工作量和未确认作息不伪装成已知。
4. **范围由程序核对。** 没说范围默认未来七天并展示；“本周/下周”按周一至周日解释，单日按该日解释，追问回答可以更新范围。模糊决策不扩大明确范围，执行限制在未来31天以内。
5. **模型选取舍，算法算时间。** 模型输出经过 schema 和操作范围校验的意图，绑定当前对象后走注册操作；时间/预算/课程冲突由确定性排程器计算。复用现有预算、取消、租约、版本、journal 与恢复机制，不加入外部 coding agent 或任意 SQL/工具执行。
6. **问题应当具体并可续答。** 实质取舍问一个有理由的问题，支持选项或自然语言；保存回答后恢复原投递并重新读取事实，最多三轮。明确指令沿用既有授权；模型推断出的长期规则、停学时段、具体块/截止修改先给建议确认。
7. **保护与结果如实展示。** 普通重排保留手动、锁定、已开始的安排。停学建议可能让出未开始的手动/锁定块，确认时说明。规则已保存、排程已计算、安排实际变化分别报告；无需移动时明确说“学习安排不需要变化”。Todo始终只读。

### 当前实现与后续边界

- 上述交互已随业务版本 `95c8cf1` 部署（schema29），代码及文档在 `agentbox/dashcampus`。实现入口和逐层证据见 [模糊调整记录](./flexible-adjustments-2026-10-04.md)、[查看请求修复](./read-requests-fix-2026-10-04.md)、[全局输入栏](./global-agent-bar-2026-10-04.md)。
- 337项隔离测试通过；真实模型已验证普通原句、斜杠原句和课程负担减轻。生产原句通过真实 API/worker，计算后无需移动；任务、课程、受保护块逐行不变。
- 真实模型追问续答尚未完整实测，只有假件的闭环验证；复杂视觉材料、真实邮件收件、主人七天试用仍按 STATUS 列为缺口。这是时间调整的有限步骤决策，不等于所有业务都具有任意自主执行能力。
- 后续增强优先补真实使用发现的断点，避免再把不常见表达直接降成任务、把缺参数直接退回设置页，或仅为展示变化而改动安排。

## 2026-10-05 Agent增强v1.1 实施中的决策

7. **试用指标只读、不美化。** 指标从已有记录聚合，不新增埋点表；样本小、无核验、无反馈时写明含义，失败与受阻照实计数。

## 2026-10-05 Agent 语义修复中的决策

依据 [语义修复提示词](../../Plan/dash-campus-AGENT-SEMANTIC-REPAIR-PROMPT-2026-10-05.md)；证据见 [语义修复验收](./agent-first-v2/acceptance-semantic-repair-2026-10-05.md)。上一节第 1、5 条被下面第 4 条取代，原文保留作历史。

1. **条件是数据，不是提示词。** 主人说的范围与“别动”变成有类型的目标约束（迁移 0033），由服务端的统一门在每条执行路径上核对；不靠补关键词或让模型“记得”。模型只能提出带逐字引用的候选，引用不在主人本人的话里就不接受。
2. **一个门，所有入口。** 路由直接执行、决策、回答续办、按钮、恢复与自动修正绑定出的命令都过 `gateCommand`：越界拒绝、按保护收窄、裁空拒绝；拒绝不落库，原因照实写。
3. **只有完整的“可以/先不要”走快路径。** 带条件、疑问、指代或改口的回答一律按整句修订同一目标；条件没有改变方案（多半理解错了所指）时照实说出来再问，不当作条件已满足。
4. **步骤凭据表。** 原“步骤就是投递事项、不另建步骤表、幂等以批次为准”不够：探索、复盘、邮件、导出没有批次。新增 `agent_step_executions`（每事项 + 操作一行，与领域写入同事务，记结果引用），恢复按凭据认领原结果。
5. **确认绑定事实。** 确认指纹含规范化命令、相关事实与约束键；执行事务内再核对，变了就重读、说明差异、重问；无关变化不打扰。
6. **异步不等于完成。** 排队/运行中是 pending，后台任务结束后由 worker 触发重新核验；邮件只核对到服务器接收，unknown 不重发。
7. **同一对话沿用保护，但不替主人拒绝新的明确要求。** 新目标只沿用保护类约束（只会拦住修改），范围与“几点后不排”不沿用；新要求只和沿用来的保护冲突时改为确认，同意只对那一步有效。
8. **计时口径说清楚。** `activeMs` 实为模型 HTTP 时间，更名 `modelMs`；180 秒上限按这个口径，不称为“全流程主动执行时间”。（已被复审后第 4 条取代）
9. **验收盲点照实更正。** G04 曾因只比较周末块而判通过，记录里周末收工被改；该结论作废并保留原记录，核对改为比较周末模板、规则与学习块。
10. **换设备从服务端目标列表续办。** `GET /api/v2/goals` 不带 `open` 时按更新时间列出最近目标；网页「最近的目标」去掉 cancelled，已完成也可以点继续。未完结筛选仍用 `open=1`。不依赖本机草稿。

## 2026-10-05 语义修复复审后的决策

复审基线 `c6b7b42`，证据见 [语义修复验收 §8](./agent-first-v2/acceptance-semantic-repair-2026-10-05.md)。上一节第 8 条被下面第 4 条取代。

1. **解除是单独授权。** 放宽比收紧危险：模型提出的解除只是候选，绑定到具体约束 ID 与目标版本，确认里点名，主人确认后才算授权，执行成功后才生效。收紧（新加约束）仍可直接生效。
2. **条件按实际落点核对。** 范围与收工时间按学习块真实的日期与起止时间核对，而不是只看命令声明的日期；核验从目标约束读回写入结果，不凭“执行成功”判通过。
3. **对象身份只解析一次。** 确认快照、保护核对都用 `commandEntities`，新增命令字段时不会一处认得、另一处漏掉。
4. **180 秒按主动执行时间。** 新增 `intakes.active_ms`（迁移 0034），worker 处理期间计时，排队与等主人不计；模型 HTTP 时间仍单独统计为 `modelMs`。不另建计时表：计时属于投递本身，随投递导出。
5. **后台未完不算完成。** 核验 pending 时目标保持进行中，结果单列 `in_background`，界面不说“已更新”也不说“在等你”。
6. **指代对不上就请主人指认。** 服务端不猜“刚才那门课”是哪个；理解出的对象不在方案里时，从方案实际要动的对象里请主人选，选项结构化处理，不再交给模型二次理解。

1. **未知就挂住，不猜。** 已过去、没有反馈的块既不算投入，也不当作没做；它的分钟数挂住同一任务的需求，等主人说。不按任务 ID 禁止多段（大任务照常拆分），也不删除或改写已有块。
2. **问的是这一段。** 每段一个持久问题，键带块的结束时间；同一任务一次只问一段，避免一口气追问。问题有自己的名额，不挤掉截止/冲突问题。
3. **回答复用现有操作。** 完成、跳过、实践记录、剩余需求都用已有命令与统一门，不新增表、不加迁移、不做单独的配置表单；没说时长不写实践记录。
4. **“做完了”默认只算这一段。** 只有这段是最后一段且盖得住剩余需求时才把整件事标完成；其他情况让剩余照常安排，不把整件事冒充完成。
5. **生产已有数据不动。** 部署后生产那两段（08:00–09:00 与 10:20–11:20）都会被识别为待反馈并挂住需求（120 ≥ 估时 60，不再新排），先问前一段、答完再问后一段；主人说整件事已完成时后一段不再问。它们的状态、实践记录由主人回答决定，部署本身不改写。
6. **记录时刻用同一时钟。** 剩余需求的报告时刻要和学习记录、块状态的写入时刻比较先后，所以用真实写入时刻，不用规划时钟 `ctx.now`；同一次回答里先记下的实际分钟算在报告里，不再从报告的剩余里扣（网页走查发现）。
