## 首次使用顺序

1. 按 `deploy.md` 配置并初始化；基础计划和记录不需要模型、搜索或 SMTP。
2. 设置 → 我的身份：只填自己确定的值。字段未填表示未知，匹配目前使用明确值比较，不擅自做专业/校区别名映射。
3. 计划 → 目标与项目：写一个学期目标及理由。也可从探索页的实践模板创建第一项实践。
4. 计划 → 可用时间、课程与缓冲：填本学期有效期、真实可用时段与课程。未设置窗口时容量显示未知，不会虚报“安排合理”。
5. 将待安排任务放入某周；有确定时间时填开始与结束。只给开始时，它表示时间点，冲突检查采用一分钟点区间，不能据此认定整个估时已经放得下。
6. 设置每周重点，关联目标 / 项目；执行后写“做了什么 / 卡在哪里”，在项目页保存成果与阶段结论。
7. 收件箱粘贴一条通知。模型未配置也会保存原文；配置后可以在详情重试提取。核对引用及未知条件后再创建任务。
8. 配置 SMTP 后，在设置中预览邮件、发送测试邮件，再按需要开启每日 / 每周摘要。`accepted` 只表示发送服务接受，不能证明入箱或已读。

日期型提醒：当天 09:00 为基准，再减去自定义提前分钟数；留空为当天 09:00。精确时刻型：截止时刻减自定义分钟数，留空默认提前 24 小时。改变提前量会递增提醒版本并取消旧的未准入提醒。

## 接口与数据变化

- Schema 11 → 14：`0012_planning_management.sql`、`0013_notice_extraction.sql`、`0014_ready_templates.sql`。
- 时间编辑：`PATCH/DELETE /api/v1/availability/:id?kind=availability|fixed-event`，必须携带 `expectedVersion`；单日例外 `PUT /availability/:id/exceptions`，首次版本为 0。
- 缓冲：`PUT /planning/buffer` 带 `expectedRevision`；墙上时间转换：`GET /planning/resolve-time?date=…&time=…&timezone=…`，遵守已有 DST 规则。
- 原文录入：`POST /inbox/manual` 必须带 Idempotency-Key；提取重试：`POST /inbox/:id/extract` 必须带所读 `revisionId`。
- 仅本条纠正现在必须提交 `revisionId`，可提交 `expectedVersion`；旧通知版本返回 409，不能折叠未读的新修订。
- 来源启停：`PATCH /inbox/sources/:id` 带名称、enabled 和版本；导入 token 校验同时检查 enabled。
- 摘要设置：`GET/PUT /digests`；`POST /digests/preview` 仅生成预览，不发邮件。
- 模板启动：`POST /practice-templates/:id/start` 带模板版本及可空的计划周，必须带 Idempotency-Key。
- 全量 JSON 包含日历例外与通知提取诊断，剔除 job ID / 来源凭证 / 调度内部状态。SQLite 备份仍保留全部个人数据。

## 升级与回退

本轮已按下述顺序完成生产升级：停止旧 web / worker、完成备份，再用与此分支匹配的源码运行迁移；核对 schema 14 与健康状态，再启动 web 和一个 worker。不可让 schema 11 的旧镜像继续连接新库。

迁移会为原任务和日历补默认字段；模板更新仅针对未经编辑的 version=1 草稿，主人修改的模板保留。schema11 →14 的真实迁移器升级测试已通过。回退应使用旧代码与升级前备份的匹配组合，不能仅回退代码。恢复流程仍进入 hold，取消旧邮件/AI 队列；通知提取状态会明确失败，可人工重试，摘要从下一周期重新调度。

## 验证边界

开发验收使用隔离的本地 SQLite、fixture 模型/搜索和捕获式 mailer。该阶段没有调用生产模型或 SMTP，没有写生产数据。后续已完成 Linux Docker 构建及生产库升级；生产邮件入箱、真实模型对不同校园原文的提取质量和真实学生使用体验仍未在本轮验证。
