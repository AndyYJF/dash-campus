## 3. 多轮例子

**例一（网页 + 真实模型，S02）**。本地开发服务器、独立临时库、真实 worker 与 `gemini-3.8-flash-high`：

1. 主人：“晚上安排太满了” → 模型读事实后问：“你是希望提早每天的学习截止时间，还是晚上完全不安排学习？”
2. 主人：“提前到九点，但只改工作日，周末别动” → 目标记下两条约束（`protect_days weekend`“周末别动”、`no_study_after`“提前到九点”，来源均为主人回答）。确认写出实际修改：工作日结束时间 22:00 → 21:00（长期）；临时允许重新安排工作日；“周末的作息、规则和安排不动，2 天不重新安排”。
3. 主人：“可以” → 执行，核验 verified；读回 `workday_end=21:00`、`weekend_end=22:00` 未变。请求账本：路由 2 次、决策 2 次，均成功。

走查中发现确认把“安排一个学习块”写成“会对外产生动作”，已改为按对象写出修改前后（`command-facts.ts` 的 `objectImpact`），并补隔离断言。

**例一续（网页 + 真实模型，同一对话沿用保护）**。改完后重启 worker，在同一对话里接着说：

4. 主人：“这周六下午三点加一小时英语听力” → 模型路由为新的一件事；新目标显示“一直守着：周末的作息、规则和安排不动（沿用你前面说的‘周末别动’）”。确认写：“和你前面说过的条件冲突：这一步会动到 2026-10-10，你说过‘周末的作息、规则和安排不动’；确认就只在这一步不按那条执行。实际修改：新增学习块：「英语听力」2026-10-10 15:00 起 60 分钟。”
5. 主人点“可以”（输入栏填入“/回答 可以”后发送）→ 新增该学习块，核验 verified；周六原有的英语阅读不变。

（走查库是先前用草稿版 0033 建的，`source` 的 CHECK 还没有 `inherited`，第一次沿用时 worker 报约束错误；只在这个临时库把该表重建为最终迁移的定义后重试。当时 0033 尚未部署，生产按最终版迁移，见 §6。）

**例二（隔离，S05）**：“这周的学习帮我理一理，周末别动” → 确认后执行 → “再优化一下”被理解成新的一件事 → 新目标沿用“周末别动”（显示“沿用你前面说的‘周末别动’”），重排授权不覆盖周末 → “周六晚上八点加一小时英语阅读”与沿用的保护冲突，不替主人拒绝，确认里写“和你前面说过的条件冲突……确认就只在这一步不按那条执行” → “可以”后只这一步执行 → 再说“这周再理一理”，周末仍不动。

**例三（隔离，带条件的回答没改变方案）**：“线代复习挪到十点” → 确认 → “好，不过刚才那门课别挪”，脚本模型把“那门课”理解成另一门、方案照旧 → 不执行，重新确认并写明“你补充的……没有改变这份方案，和上一版完全一样；如果你指的是下面要改的对象，请直接说不改它” → “先不要” → 0 批次。
